# Curriculum review: learner capability first

Reviewed for the user's stated novice/junior starting point. No learner submissions were available, so placement and ability remain unassessed.

| Finding from the previous material | Why it obstructed learning | Change |
| --- | --- | --- |
| Lab 01 asked for a field across schema, UI, normalizer and report | First task assumed several untaught languages and boundaries | Node-only function exercise, then seven foundations sessions; cross-stack work comes later |
| Roadmap followed ten product milestones | Building a platform and learning to own a change require different orders | Gates progress from small changes to independent delivery and judgment |
| Early labs pointed at whole API/worker files | Too much unfamiliar code to isolate cause and effect | Narrow source entry points, tiny fixtures, explicit exit tasks |
| Most evidence was authored by the builder | Re-running a harness did not demonstrate learner authorship | Learner tests, failure traces, assistance records, transfer tasks, later revisits |
| Twelve reflections were the main visible progress | Reflection did not distinguish scaffolded from independent work | Separate competency dimensions and evidence-backed gates; retain reflections |
| Recovery and infrastructure dominated next-task guidance | Advanced setup displaced basic coding, debugging, SQL and UI work | Foundations-first next contract; advanced systems as later electives |

The revised ordering is a curriculum design decision for this learner, not a measured learning outcome. We adapted the read/predict/run/modify/make structure described by the [National Centre for Computing Education](https://teachcomputing.org/blog/using-primm-to-structure-programming-lessons/). That source concerns teaching programming in schools; effectiveness for this adult learner must be assessed from their attempts and feedback.

For career calibration, GitLab's public [intermediate framework](https://handbook.gitlab.com/handbook/engineering/careers/matrix/development/dev/backend/intermediate/) emphasises independent delivery of bounded solutions and useful review. Its [senior framework](https://handbook.gitlab.com/handbook/engineering/careers/matrix/development/dev/backend/senior/) adds ambiguous work, broader decisions and coaching. These are examples from one employer, not universal titles. The roadmap uses that distinction and requires real collaboration evidence for senior practice.

Validation of the curriculum covers executable examples, reference checks, known wrong implementations, paths, prerequisite order, and progress preservation. It cannot validate teaching effectiveness, independent learner skill, or senior readiness before the learner does the work.
